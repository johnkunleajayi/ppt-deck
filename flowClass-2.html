5. Start Conditions vs. Decision Elements

Start Conditions

"Should the Flow run at all?"

Gates entry into the Flow. Non-matching records are filtered out instantly at zero computational cost.

LeadSource = 'Website'

Decision Element

"What path should the Flow take?"

Evaluates records inside the Flow to choose between multiple downstream outcomes.

High vs. Med vs. Low

Simple Rule: Start conditions = Should it run? | Decision = What should it do?

6. Understanding $Record

$Record represents the exact record currently being processed by the Flow.

Lead Object Context

  • $Record.FirstName → First Name
  • $Record.Company → Company Name
  • $Record.AnnualRevenue → Annual Revenue
  • $Record.LeadSource → Lead Source

Case Object Context

  • $Record.Subject → Case Subject
  • $Record.Status → Case Status
  • $Record.Priority → Priority Picklist
  • $Record.Origin → Case Channel Origin

17. Critical Flow Design Habit

Never open Flow Builder immediately! Translate business requirements into logical pseudo-code first:

1. Written Logic Formula

WHEN: Case is created
CHECK: Priority field value
IF: Priority = High
THEN: Update Status = Escalated

2. Flow Builder Mapping

Trigger: Case Created
Decision: Evaluate $Record.Priority
Outcome: High Priority
Action: Update Records Element

18 & 19. Pitfalls & Debugging Framework

4 Beginner Mistakes

  • Putting multi-branch rules into Start Conditions.
  • Neglecting to handle the Default Outcome path.
  • Testing only 1 outcome branch instead of all.
  • Building in canvas without understanding data.

Systematic Debugging Questions

  1. Did the Flow trigger?
  2. What values were passed into $Record?
  3. Which Decision outcome path was selected?
  4. Did the update action execute correctly?
  5. Was the target record updated in database?
